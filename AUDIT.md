# Audit: boto3 AWS Emulation Lab

Self-audit against the standing project standard, written after
the generated results and before this file was committed. Verdicts
were published either way, including the refuted one.

Under the portfolio standard v2 this file is the study's report
(the README layout table maps it). Grades are internal and are not
published here; the limits that the earlier grade itemized are kept
below as threats to validity.

## Verdict under the standard (2026-11-08)

Functional. Tests pass in CI on Python 3.11 and 3.12, the scored run
and the results generator are one documented command, and the
system under study (moto 5.2.5 in server mode, driven by boto3) ran
all 30 frozen rows end to end, with the raw records in
results/scores.json. Every hypothesis is scored in RESULTS.md, the
refuted H2 included. Not Evaluated: the declared field profile,
Systems and infrastructure, reliability, asks for stated recovery
targets (availability, RTO, RPO), timed drills, monitoring that
would catch each drill's fault, and a runbook. This study is an
emulator conformance study and has none of the four, so the
profile is not met.

## Headline claim check (Jev)

The headline verdicts (24 of 30 MATCHES, H1 CONFIRMED, H2
REFUTED, H3 CONFIRMED, the per-service counts and the six named
non-MATCHES rows) were screened with the house claim_check gate
(TypeSafe Jev, model jev-1.13.0, one noul question "supported").
Jev returned noul 0.31, which is the REVIEW band (clear at 0.85,
block at 0.10), so every figure was verified by hand against
results/summary.json and results/scores.json before anything was
published, and all figures agree. The screen, its route and the
hand verification are recorded in results/jev-claim-check.json.

## How the evidence is protected

1. Pre-registration before code and results. PREREGISTRATION.md is
   the root commit (2b2659d, to be tagged proposal-v1); BEHAVIOURS.md
   followed in 28bfcf2, both before the harness (d9d1913) and the
   results (624027e). GitHub's activity log shows the same push
   order. tests/test_layout.py pins the SHA-256 of both files as
   committed, so a one-byte change fails CI.
2. Numbers come from scripts. RESULTS.md and results/summary.json
   are generated by scripts/make_results.py from the raw records in
   results/scores.json. CI regenerates both and fails on any diff,
   and a test checks that the README headline counts equal
   results/summary.json.
3. The verdict rules are code with tests. tests/test_scoring.py
   checks the 70 percent line on both sides, the two-row H3 rule
   and that an ERROR row forces INCONCLUSIVE.
4. No real AWS, enforced in code. src/factory.py forces every client
   to a 127.0.0.1 endpoint with placeholder credentials and disabled
   instance metadata; tests/test_guard.py fails if a client points
   anywhere else.
5. Pins are part of the result. requirements.txt pins every
   package, and results/versions.json records the versions and
   machine of the scored run.

## What was verified by hand

- The pre-registration is the root commit (2b2659d) and predates
  the harness and every run; BEHAVIOURS.md was committed before
  the harness (28bfcf2 before d9d1913).
- Every number in README.md and RESULTS.md traces to
  results/scores.json through scripts/make_results.py. The counts
  were recomputed from the raw records during the Jev hand
  verification and agree.
- The three run-1 ERROR rows were root-caused by probes before
  any fix (DECISIONS.md D5), and only the four affected rows were
  rescored, through scripts/rerun_rows.py; the other 26 records
  are the original run's, untouched.
- No real AWS was touched: the factory forces 127.0.0.1, the guard
  test fails on any other endpoint, the credentials in code are
  obvious placeholder strings, and instance metadata is disabled
  in the harness process.
- Docker is absent on the machine of record (verified, DECISIONS.md
  D1), so no LocalStack arm exists and nothing in the build depends
  on it.

## Threats to validity

The limits of this study, stated so a reader can weigh every verdict.

- **The Lambda execution rows are environment-bound, not
  semantic.** L-02 and L-03 are UNSUPPORTED because this machine
  has no Docker, not because moto's invocation semantics were
  measured and found wrong. On a Docker host those rows might
  match, diverge, or fail differently, and this study cannot say
  which. Two of the seven Lambda rows therefore carry less
  information than the design intended. An independent reviewer's
  rerun on a Docker host reported MATCHES for both (26 of 30); that
  is a separate measurement on another machine, not part of the
  scored record, and it changes no verdict here (DECISIONS.md D7).
- **One emulator only.** The LocalStack arm was dropped
  (D1), so every claim in this study is a claim about moto 5.2.5,
  while the research question says "a local emulator". The README
  names moto throughout, but the comparison the question gestures
  at was never run.
- **One pass per row.** Each row was executed once in the
  scored run (plus the registered subset reruns). The
  timing-sensitive rows (Q-02, Q-04, Q-05, F-01) rest on single
  passes with wide margins, not on repetition statistics, so
  flakiness in either direction would not have been detected.
- **The H2 refutation leans on kind SQS coverage.** All 10
  SQS rows matched, but the frozen list omits SQS areas where
  emulators commonly stray: delay queues, message retention,
  batch APIs, and ordering across multiple FIFO groups. H2 is
  REFUTED as frozen; a harder list might have confirmed it.
- **The presigned-URL divergence is only half isolated.**
  S3-09 measures boto3's default signing against a custom
  endpoint. The s3v4-configured variant, which would separate
  "SDK default" from "emulator behaviour" completely, was not
  measured.
- **S3 Select coverage is one query and one format.** A
  single CAST comparison over CSV. JSON input, LIKE predicates
  and aggregate functions are unmeasured, so the UNSUPPORTED
  verdict bounds the documented subset narrowly.
- **The attribute MD5 oracle lacks an independent vector.**
  The documented algorithm in src/oracles.py was checked against
  the emulator, not against a worked example published by AWS,
  so a shared misreading of the document by oracle and author
  would pass silently. (Name-order invariance and change
  sensitivity are unit-tested; the algorithm text is cited.)
- **One assertion demoted to a note.** S3-05 records the
  HTTP status of the deleted-version read as a note rather than
  an assertion, because the frozen expectation named only the
  error code. The record is complete, but the scoring surface is
  one assertion thinner than its neighbours.
- **Classification code changed after run 1 saw the rows.**
  L-02, L-03 and S3-12 first scored ERROR; the detection of the
  emulator's refusal text was added after those records were seen,
  then only the affected rows were rerun (DECISIONS.md D5). The
  change was declared before the rerun and no expectation moved,
  but the run-1 records themselves were overwritten in
  results/scores.json and are not kept in the repository, and the
  rerun is not noted on the L-02 and L-03 records as Section 5 of
  the pre-registration asks (DECISIONS.md D6). The run-1 records
  were never committed, so they cannot be recovered from history.
  Since 2026-11-08 the generator adds the rerun note, with each
  row's run-1 status, to all four rows in RESULTS.md, and
  scripts/rerun_rows.py keeps every record it replaces in
  results/replaced-records.json (DECISIONS.md D7).
- **Ordering is proven by commit and push order, not by
  timestamps on the evidence.** The four commits were pushed to
  GitHub at 21:00:11, 21:00:53, 21:05:03 and 21:07:46 UTC on
  2026-11-08 (GitHub activity log), so the pre-registration was
  public before any harness or result. The records in
  results/scores.json carry no run timestamps, so the history
  cannot show when the scored run happened inside the last gap.
- **One machine of record, not reproduced elsewhere yet.** The
  scored run is from htch-runtime. CI runs the unit and smoke
  tests (three rows against a live loopback moto server) and
  regenerates RESULTS.md from the recorded records; it does not
  rerun the 30 scored rows.

## Left undone, with reasons

- LocalStack arm: impossible on this machine (no Docker, D1).
- Lambda execution semantics: blocked by the same absence; the
  rows are scored UNSUPPORTED with the emulator's error quoted,
  which is the honest result for this machine of record.
- A repetition study for the timing rows: outside the frozen
  design; noted above as a deduction instead of quietly added.

Nothing was published outside this GitHub repository. No real
AWS account, credential or endpoint was used. No spend.
